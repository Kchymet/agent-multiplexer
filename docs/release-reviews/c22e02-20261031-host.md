## Findings: replay acceptance, recovery and revocation

**Observed — durable acceptance remains distinct from execution.** `internal/access/authority.go:941–989` retains signed body, boot nonce, request ID, time-window, current credential generation and revoked-state validation. It now holds the registry **read** lock through `acceptReplay` rather than the write lock. Revoke/rotate/close still need the registry write lock, so none can commit between that validation and journal acceptance. This is not a promise that already accepted work can be recalled; `Valid`/final effect authorization remain separate.

`internal/access/replay_journal.go:341–367` makes the replay decision under `replayMu`, reserves the request before append, and keeps it consumed if append/sync errors. `:301–333` serializes each shard's append and file sync before success. Duplicate acceptance remains `ErrReplay`, not cached success or exactly-once execution. A caller observing an uncertain outcome must not blindly retry a non-idempotent operation with a new request ID.

**Observed — crash-ordering design is sound under its stated storage assumptions.** New shard names are directory-synced before installation (`replay_journal.go:254–283`). Compaction locks the ledger and all shards for rotation, captures a snapshot, then writes that snapshot before deleting prior generations (`:388–438`). New acceptance may continue in the new generation while the snapshot is written. Recovery unions snapshot plus all journals before opening new shards (`:204–238`). Journal/capacity failures return errors rather than accepting without persistence (`:310–325,358–365`). Rotation failures leave no installed shard and retain old files. Close joins compaction before closing the journals (`:453–470`, `authority.go:278–300`).

**Acceptance limit — torn tail versus corruption.** `readJournal` deliberately discards an incomplete/zero-filled tail and also a complete-size final record with invalid checksum/JSON (`replay_journal.go:139–169`). It cannot distinguish a torn unacknowledged write from later corruption of an acknowledged final record using that checksum alone. The existing tail test appends a synthetic **unacknowledged** sixth record after five accepted records (`replay_journal_test.go:117–157`); it is not arbitrary disk-corruption proof. Non-final corruption returns an error and prevents opening (`:160–201`). The phrase “fails open” in the comment/test name means **the Open operation fails**, not insecure authorization success. The boot nonce additionally rejects old-boot signed requests (`authority.go:945–948`); recovery tests deliberately restore the old boot ID to test the ledger independently (`replay_journal_test.go:58–70`). No replay exploit or actual power-loss outcome is claimed.

**Focused follow-up proposal, nonblocking on evidence obtained:** add a pure access-package fault test for record-file sync failure, conservative same-process consumption, subsequent acceptance/compaction, and reopen. Existing new sync-injection tests primarily cover directory sync. If the release promises recovery from partial write failures as well as torn final crash writes, add a deterministic file-I/O seam to test failed/partial append followed by a successful append and restart; decide whether that shard should be quarantined until rotation. Current source does not retire a shard on append/sync error (`:321–325`). This is a fault-path acceptance proposal, not a proven loss or bypass, and requires no provider process. Keep any stronger corruption guarantee explicitly separate from ordinary trusted-local-filesystem crash consistency.
